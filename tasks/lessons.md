## 2026-06-01: JMA注意報は timeSeries を持たない種別がある（濃霧・乾燥など）
- **状況:** 濃霧注意報が発表5/28から4日間表示され続け、AIにも渡り続けた。期間表示も出なかった。
- **原因:** 濃霧(14)等は top-level `areaTypes` に `status:発表` のみ存在し、`timeSeries` に時系列(levels)を持たない。さらに当該地域の唯一の timeSeries が `雷危険度` の複合オブジェクト形式で、`buildValidPeriodMap` がスキップ → `validPeriodMap` 空 → `startMs/endMs/validPeriod` 全て undefined。結果、期限ベースの除外もAIの24hフィルタ(startMs基準)も発動しなかった。
- **ルール:** 期限情報のない注意報は `reportDatetime`（発表時刻）を基準に経過時間で除外する。除外判定は `fetchJmaWarnings` の1箇所に集約し、UI・AI・ガントバーを単一ソースで制御する（AI側に別基準の重複フィルタを置かない＝基準ズレによる不整合を防ぐ）。期間表示は終了時刻が無い種別では発表時刻のみ表示（JMAは濃霧等に終了時刻を提供しない）。

## 2026-06-06: 共有コンポーネントの型変更時に全使用箇所の型注釈更新を漏らした
- **状況:** `WarningBar` の props を `number → string` に変更した際、`DailyForecast.tsx` の `warningToBar` の return 文は修正したが、関数の戻り値型注釈 `{ left: number; width: number }` を更新し忘れた。ローカル tsc は通過したがリモートビルドで2度エラー。
- **原因:** return 文の値と型注釈が別行にあり、片方だけ修正して確認が不完全だった。ローカルの tsc が通過した理由は不明（tsconfig のスコープ差異の可能性）。
- **ルール:** 共有コンポーネントの props/返値型を変更したら `grep -n "warningToBar\|WarningBar"` 等で全使用箇所を列挙し、**return 文と型注釈を両方**変更する。変更後は必ず `npx tsc --noEmit` を実行して確認すること。

## 2026-07-04: Vite の `VITE_*` 環境変数はビルド時に焼き込まれる（後付け・改名で沈黙）
- **状況:** 本番でアナリティクスが全く計測されなかった。Cloudflare の env 一覧には値が登録済みに見えたのに GA4 リアルタイムに何も出ない。原因は変数名が `VITE_FIREBASE_MEASUREMENT`（`_ID` 欠落）で、コードが参照する `VITE_FIREBASE_MEASUREMENT_ID` が空だったこと。
- **原因:** Vite は `import.meta.env.VITE_X` を**ビルド時に文字列リテラルへ置換**する（ランタイム参照ではない）。①名前が1文字でも違えば `undefined` になり無言で機能停止 ②env を後から追加/修正しても、既存の本番バンドルは変わらず、**リビルドするまで反映されない**。エラーも出ないため気づきにくい。
- **ルール:** `VITE_*` を追加/変更したら (1) コードが参照する名前と**完全一致**しているか grep で照合（`grep -rn "VITE_FIREBASE_MEASUREMENT_ID" src/`）、(2) 変更後は**必ず再デプロイ（リビルド）**する、(3) 反映確認は「本番バンドルに期待値の文字列が焼き込まれたか」を直接検証（`curl -sL <本番>/assets/index-*.js | grep '期待値'`）。なお Cloudflare Pages は `.html` を正規URLへリダイレクトするため、静的HTMLの検証 curl は必ず `-L` を付け拡張子なしURLで確認する。

## 2026-06-01: 日付計算で `new Date(str)` + `toISOString()` がTZズレを起こす
- **状況:** 日別の夜間降水量が時間別の合計と一致しない。6/3未明の雨4.9mmが2日ズレて6/1夜間に合算されていた。
- **原因:** `new Date(date + 'T00:00:00')` はローカル時刻（JST）として解釈され、その後 `toISOString()` でUTCに変換すると9時間戻って日付が1日余分にズレる。`setDate(-1)` と合わせて計2日ズレた。
- **ルール:** カレンダー上の日付加減算は必ずUTC基準で行う。`src/lib/dateUtils.ts` の `addDays()`（`Date.UTC` ベース）を使う。ローカル時刻Dateを生成して `toISOString()` で日付を取り出す処理は禁止。

## 2026-10-04: Open-Meteo archive は同時接続数に上限がある（並列取得で 429）
- **状況:** 今年のあゆみの帯が実画面で表示されなかった。単体テストは全件成功していた。
- **原因:** 年ごとに `fetchWeatherData` を並列で6〜7本呼んだ（各年さらに年境界の要求が2本）。archive API は同時接続が多いと `429 {"reason":"Too many concurrent requests"}` を返し、`Promise.all` が失敗→フックが静かに hidden にしていた。モックしたテストでは検出できない。
- **ルール:** archive API へは**並列で叩かない**。複数年は start_date〜end_date の1リクエストにまとめる（`fetchDailyActuals`）。外部 API を使う新機能は、完了前に必ず実画面（dev サーバー＋ネットワークログ）で取得成功を確認する。「失敗を静かに隠す」設計の機能ほど、実画面確認を省略しないこと。

## 2026-10-04: 表示専用の親に pointer-events:none があると、子をボタン化しても押せない
- **状況:** ヒーローの節気名をボタンにしたが、実画面でタップが届かなかった（単体テストの fireEvent.click は通る）。
- **原因:** 親 `.sky-hero__sekki` に `pointer-events: none`（表示専用だった頃の指定）が残っていた。jsdom はヒットテストをしないのでテストでは検出できない。
- **ルール:** 既存の表示要素を操作可能にするときは、祖先の `pointer-events` を grep で確認し、Playwright の実クリックで検証する。

## 2026-10-04: Open-Meteo 無料枠は「期間の長さ」でも消費する（長期間の要求を毎回出すと上限→予報まで拒否）
- **状況:** 季節のあしどり追加後、アプリを開くとトップに「取得元がメンテナンス中…」が出た（予報の取得が 429 で拒否）。時間を置くと回復。
- **原因:** 無料枠は IP ごとに 1分600・1時間5,000・1日10,000 回で、2週間を超える期間は2週間ごとに1回分として数える。約6〜7年分を開くたびに取得（1回で約90〜180回分）＋検証の自動撮影の繰り返しで1時間の上限を超え、同じ IP の予報要求まで拒否された。429 を「メンテナンス中」と表示していたため原因が見えにくかった。
- **ルール:** 長期間の実績は、変わらない過去年を端末に保存して取り直さない（`fetchDailyActuals`）。新しい取得を足すときは「1回で何回分消費するか × 開く頻度」を見積もる。429 は「アクセス集中」として別の文言にする（`weatherFetch` の `busy`）。実画面の自動検証を繰り返すときは、外部 API の上限を消費していることを意識し、回数を絞る。

## 2026-10-04: Cloudflare Pages の1画面アプリ既定動作で、更新直後の CSS 要求に HTML が返り保存されて画面が崩れた
- **状況:** 本番（カスタムドメイン）をスマホで開くと真っ白→後に装飾なしで崩れた。PC・develop・pages.dev では正常。端末のサイトデータ削除でも直らず。自己診断で「CSS の URL に `text/html`（トップの HTML）が返っている」と判明。
- **原因:** Pages は 404.html が無いと「存在しないパスにトップの HTML を 200 で返す」。更新直後の配信の切り替わり時に CSS 要求へ HTML が返り、Service Worker（等）が CSS として保存。CSS のハッシュ名が複数回の更新で同じだったため取り直されなかった。描画エラーではないのでエラー境界でも捕捉できなかった。
- **ルール:** 静的アセットの欠落は 404 を返す（`public/404.html` を置く）。CSS が当たらない事象に備えて `cssGuard`（`:root` トークンで検出→誤保存の削除→読み直し→GA4記録）を残す。「端末だけ・ドメインだけ」の不具合は、推測を重ねる前に端末で動く自己診断を出して事実を集める。

## 2026-10-06: 画面を止める演出（100svh の枠）は、中身の高さの合計を画面サイズごとに見積もる
- **状況:** LP 計画の節気の章で、100svh・overflow:hidden の枠に見出し・列・カードを縦に積み、1280×800 でカード下部が約135px 切れる設計になっていた（計画レビューで指摘）。DOM の存在を見るテストでは検出できない。
- **ルール:** 固定高さの枠に中身を入れるときは、残りの高さに合わせて縮める（`minmax(0,1fr)`＋`container-type: size`＋`cqh`）。計画段階で CSS を隔離 HTML に起こし、Chromium で複数の画面サイズの位置を実測する。動きを減らす設定の「別表示」も、重なり・非表示が無いかを実測で確かめる。「一度見えたら true」のフックを、繰り返し動く処理の開始条件に使わない（画面外で止まらない）。

## 2026-10-06: 章ごとの css と共通 css は「共通が先」に読み込まれる形にする
- **状況:** LP の共通 `lp.css` を LandingPage の最後で import していたため、章の css（`.lp-sekki { padding: 0 }` など）より後に当たり、同じ詳細度の共通指定（`.lp-ch { padding }`・`.lp-vertical`）が章の指定を上書きした。余白が二重になり見出しが崩れ、スマホの横書き切り替えも効かなかった。jsdom のテストでは検出できない。
- **ルール:** 共通スタイルは、各章が必ず import する部品（`primitives.tsx`）から読み込み、章の css より先に評価されるようにする。css の当たり方は実画面の撮影で確認する。

## 2026-10-06: `npm test -- <パス>` は1ファイルに絞れない（script の `vitest run src` が優先）
- **ルール:** 1ファイルだけは `npx vitest run <パス>`。計画書やサブエージェントへの指示にもこちらを書く。

## 2026-10-06: build.target が es2020 でも、正規表現の後読み（`(?<=…)`）は変換されずに出力される
- **状況:** LP の `split(/(?<=、)/)` がそのまま出力され、iOS Safari 16.4 未満では LP のチャンク全体が読み込めない状態だった（最終レビューで発見）。
- **ルール:** 後読みを使わない（`match(/[^、]+、?/g)` などで書く）。build 後に `grep -c "?<=" dist/assets/*.js` で確認する。

## 2026-10-06: ストアの初期化から呼ぶ関数が、後ろで宣言した const を読むと TDZ で必ず失敗する
- **状況:** `create()` の初期値で `loadGuestWeatherCodeMode()` を呼び、その関数が create より後ろの `const GUEST_WEATHER_CODE_MODE_KEY` を読んでいた。関数宣言は巻き上がるが const は未初期化で ReferenceError → try/catch に握りつぶされ常に既定値。テストは setState で状態を上書きしていたので気づけなかった（Codex レビューで発見）。
- **ルール:** モジュール初期化中に使う定数は使う場所より前に置く。「起動時に保存値を読む」処理は、保存値を入れてから `vi.resetModules()`＋動的 import で読み込むテストを書く。

## 2026-10-07: 読みやすさのための背景は、LP 全体の淡い色調に合わせる
- **状況:** 太陽と重なる項目名を読ませるため濃紺の札に白抜きにしたところ、「背景色が強すぎ、全体のバランスに合わない」と指摘された。
- **ルール:** 空の LP では、読みやすさを濃い背景で確保せず「淡い背景（すりガラス）＋濃い文字」で確保する。強調要素を足すときは、周囲の要素と並べた撮影で色の強さを比べてから出す。
